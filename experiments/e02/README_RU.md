# E02: переход к независимой разметке

Статус на 14 ноября 2026: **подготовка development-эксперимента**. Подтверждения H1-H3, независимого human gold и оценки качества на новых рынках нет.

## Что добавлено

- `workflow.py`: аудит очереди и пересечений split; счётчики для частично известного эталона.
- `preparation/`: 12 выбранных калибровочных пар в двух одинаковых пустых формах. Обе формы заполняют разные люди, отдельно друг от друга. Никаких предложенных моделью меток в них нет.

- В `terms/` сохранены два PDF, на которые ссылается текущая Kalshi series metadata. `terms_manifest.json` фиксирует URL и hashes. Их применимость, приоритет и полнота ещё не удостоверены.
- Тесты защищают знаменатели, различие ошибки формата и отказа, hash входа, невозможный эталон и границы split.

Старый E01 не изменён. Его `possible`, `possible_witness` из старой инструкции и новый `possible_with_witness` не смешиваются автоматически. E02 использует только `forbidden`, `possible_with_witness`, `unknown`.

## Запуск

Из корня репозитория, Python 3.11+, без дополнительных библиотек:

```bash
python3 -m unittest discover -s experiments/e02 -p 'test_*.py' -v
python3 experiments/e02/workflow.py prepare --output tmp/e02-new-preparation
python3 experiments/e02/workflow.py check-splits --pairs experiments/e02/preparation/reviewer_a.jsonl
```

Выходная папка preparation должна быть новой: команда отказывается перезаписывать человеческую работу. Текущие 40 пар относятся только к dev. Пустой список конфликтов не удостоверяет отсутствие похожих шаблонов: `template_family_ids` ещё должны определить люди.

Новый ограниченный сетевой сбор, без ключей и платных вызовов:

```bash
python3 experiments/e02/collect_public.py --output tmp/e02-current-api
```

Сетевой повтор получает **текущие**, а не исторически идентичные ответы. Для воспроизведения снимка 14 ноября используйте сохранённые raw-файлы и manifest. Эта команда получает API-пакет; два дополнительных PDF загружены отдельно по точным URL из `raw/kalshi_series.json` и зарегистрированы в `terms_manifest.json`.

## Как разметить 12 пар

1. Выдать каждому человеку только его форму и эту инструкцию. Скрыть `selection_audit`, ранги и модельные ответы из week1.
2. Сначала собрать действующий пакет правил. `source_completeness` описывает, что найдено и что отсутствует; наличие двух API-полей не удостоверяет полноту.
3. Указать бинарную область и предпосылки. Для каждого состояния записать статус; для запрета - основание и ссылки на точные документы/фрагменты; для возможного - конкретный согласованный сценарий; для неизвестного - причину.
4. Каждый человек фиксирует свой ID и дату. Затем сравнить исходные ответы, посчитать согласие и разрешить расхождения отдельно. Не заменять исходные ответы согласованной версией.
5. Согласованный эталон выгрузить в отдельный файл; исходные annotations сохраняются. Даже после этого текущий набор остаётся dev.

Эта форма - соглашение о данных, **не автоматический валидатор достаточности доказательств**. `possible_with_witness` в scorer означает заявленный статус; корректность свидетеля проверяется отдельно.

## Входы scorer

Эталон: JSONL-строки с `case_id`, `packet_sha256`, `task_scope_sha256` и `states`. Predictions имеют те же ID/hashes, `states` и `format_error` (null или строка). Для ошибки формата `states` должен быть null. Для осознанного отказа нужны четыре `unknown`, `format_error=null`. Все строки когорты сохраняются, включая неудачные вызовы.

`packet_sha256` в подготовленных формах вычислен как SHA-256 от UTF-8 `json.dumps({"A": A, "B": B}, sort_keys=True, ensure_ascii=False)`. Аннотации не входят в пакет. При изменении правил создайте новую версию пакета и новые predictions. Не подставляйте старый hash к новому тексту.

До inference и экспорта эталона отдельно зафиксируйте **общее задание** `task_scope`: бинарную область, допущения, включённые исключения и перечень действующих документов. Его SHA-256 вычисляется той же канонической JSON-сериализацией и сохраняется как `task_scope_sha256`. В пустых формах оба поля null, потому что область ещё не согласована. Scorer требует непустые совпадающие hashes; совместимость содержания области и правил проверяют люди. Нельзя оценивать ответ для обычной публикации по эталону, который включает задержки, даже если A/B совпадают.

```bash
python3 experiments/e02/workflow.py score --reference PATH_TO_ADJUDICATED_JSONL --predictions PATH_TO_PREDICTIONS_JSONL
```

Пути в последней команде - параметры для будущих реальных файлов, которые ещё не созданы.

## Значение метрик

| Поле | Знаменатель / смысл |
|---|---|
| reference_evaluability | Известные эталонные состояния / все четыре состояния всех пар |
| state_coverage_all | Выданные моделью не-unknown статусы / все состояния |
| known_state_coverage | Выданные статусы на известных эталонных состояниях / известные эталонные состояния |
| selective_known_state_error | Ошибки среди оценимых выданных статусов |
| forbidden_precision_on_known_reference | Верные запреты / запреты с известным эталоном |
| unsupported_forbidden_on_unknown_reference | Выданные запреты, истинность которых эталон не устанавливает |
| exact_pair_accuracy | Точное совпадение четырёх статусов только на полностью известном эталоне |
| format_error_pairs | Невалидные ответы; учитываются отдельно от семантических отказов |

Нулевой знаменатель даёт null. Неподтверждённые запреты не объявляются ошибками и не исчезают из отчёта. Все четыре запрещённых состояния у модели сохраняются как содержательная несогласованность; такой эталон отвергается. Интервалы, макроагрегация по семействам и кривые риск-покрытие в E02 ещё не реализованы.

## Что сделать следующим

Согласовать второго разметчика и 8-12 полных пакетов. Проверить новую CPI-пару при обычной публикации и при задержке: у Polymarket предусмотрено переключение на предыдущий доступный месяц, в Kalshi API описано продление при shutdown, а связанный PDF содержит иные сроки. Это повод уточнить область и применимость документов, а не автоматически присвоить метку ошибки площадке.

Для H1 разметить небольшой полный блок, включая кандидатов вне top-k. Для H2 обе ветви должны возвращать одинаковые четыре статуса, с одинаковой возможностью отказа. H3 запускать только после этого и сравнивать с дополнительным обычным вызовом на том же исходном ответе и сопоставимом бюджете.
