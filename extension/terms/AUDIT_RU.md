# Аудит полных правил реальных пар Kalshi

Проверка выполнена 29 сентября 2026 по Дубаю (скачивание начато 28 сентября, 21:14 UTC). Это предварительная исследовательская проверка спецификаций, не независимая gold-разметка и не заключение о гарантированных фактических выплатах. Исходный `pilot/` не изменялся. Все документы, ответы API, даты и SHA-256 сохранены отдельно в [manifest.json](manifest.json).

**Основной результат:** вложенность двух порогов одного CPI-выпуска подтверждается алгеброй при общем значении резолюшена. Более интересная пара «декабрьский YoY CPI >5% ⇒ любой месяц 2026 ≥5%» остаётся **условной** после чтения PDF: полные правила обнаружили разные резервные процедуры и сроки, а не сняли все вопросы. Это полезный результат аудита, а не неудача сбора данных.

## 1. Что именно проверено

Получены текущие series metadata семи серий, семь ссылочных PDF с полными terms (шесть уникальных документов), соответствующие certification PDF и официальный DCM Rulebook v1.29. Полные terms прочитаны; в certification проверены относящиеся к обсуждаемым CPI сериям приложения с правилами, а в Rulebook — §§6.3, 7.1–7.2. Страницы ниже — физические страницы сохранённых PDF, нумерация с единицы.

У двух исходно сохранённых серий `KXCPIYOY` и `KXLCPIMAXYOY` новые metadata совпали со старым ответом по всем полям. Однако `last_updated_ts` серии и неизменный URL **не доказывают**, что файл PDF имеет ту же историческую редакцию. Это отдельно полученные текущие документы; их нельзя задним числом объявлять частью исходного snapshot. Certification — исторический документ первоначального листинга, а не автоматически последняя редакция terms.

## 2. Декабрьский YoY против любого месяца года

A = `KXCPIYOY-26DEC-T5.0`; B = `KXLCPIMAXYOY-27-P5`.

### Проверенные поля и расхождения

| Поле | A | B |
|---|---|---|
| Источник | BLS, подтверждён API и S1 с.1 | BLS, API и S2 с.1 |
| Метрика | All-items CPI-U без сезонной корректировки; 12 месяцев до декабря; опубликованное значение с одним десятичным знаком (S1 с.1) | Набор значений CPI-U без сезонной корректировки за месяцы периода; есть неоднозначная формулировка, описанная ниже (S2 с.1) |
| Период API | 12 месяцев, заканчивающихся декабрём 2026 | Любой статистический месяц 2026; `-27` в ID сам по себе не означает период 2027 |
| Порог API | Строго >5.0% | ≥5%; PDF-шаблон содержит оператор above, без явного inclusive-варианта |
| Версия данных | Значение на Expiration; позднейшие revisions исключены | То же правило относительно собственной Expiration |
| Время по terms | 8:31 AM ET; latest expiry через три месяца после планового выпуска (S1 с.1–2) | 8:31 AM ET; раннее завершение при удовлетворении условия, после выпуска последнего месяца либо через 14 дней после запланированного выпуска (S2 с.2) |
| Задержка | API secondary отдельно добавляет продление при government shutdown | Такое продление прямо содержится в S2 с.2 |
| Нет данных | S1 с.1 задаёт отдельный вычисляемый fallback | В S2 нет той же формулы |

S1 fallback использует отношение последнего доступного CPI к значению за 12 месяцев до него, возведённое в степень **13/12**, минус 1. Степень сверена визуально по PDF: это не ошибка извлечения текста. Здесь мы не исправляем формулу и не предполагаем отсутствующее правило масштабирования процентов; это ещё одна причина сохранять исходный текст и не выводить финансовые гарантии автоматически.

В S2 Underlying одновременно встречаются слова “one-month” и “measured year-over-year”. Приведённый далее пример и market primary указывают на YoY. Однако раздел Instructions в самом документе обозначен как справочный, не binding. Наш интерпретатор не должен молча устранять такое расхождение. Отдельно сохраняется `above` в шаблоне против `at least` в API. Для направления **>5 ⇒ ≥5** сама эта пограничная разница не разрушает арифметику; она важна для точного определения выплат и обратных выводов.

### Что можно и чего пока нельзя вывести

**Доказано внутри явно ограниченной модели:** если обе стороны используют одинаковые опубликованные декабрьские YoY-данные, декабрь входит в период B, а стандартная бинарная процедура и согласованная обработка публикаций сохраняются, A=1 ⇒ B=1. Декабрь сам даёт требуемый свидетель месяца. Обратное неверно: другой месяц может иметь 5.1%, а декабрь — 4.9%. Это гипотетический свидетель, не наблюдённые данные.

**Универсальная связь фактических выплат не установлена.** A может использовать fallback или более поздние данные, B — иной предел ожидания и иную историю раннего завершения. Чтобы получить полный контрпример, требуется ещё показать, что соответствующие исключительные ветви могут применяться совместно; одно различие сроков этого не доказывает. Поэтому статус — `conditional_A_implies_B`, а состояние 10 для полного, неограниченного договора — `unknown`, не доказанно возможное и не доказанно запрещённое.

Проверяемая задача для следующего этапа: восстановить применимые изменения условий/уведомления и нормализовать release time, statistical month, revision cutoff, fallback branch отдельно. Высокий NLI entailment score по двум кратким предложениям не закрывает эти поля.

## 3. Пороговые positive controls

### CPI октября: >0.9% ⇒ >0.8%

A = `KXCPI-26OCT-T0.9`; B = `KXCPI-26OCT-T0.8`.

S3 с.1 уточняет: это месячный, сезонно скорректированный CPI-U с одним десятичным знаком, BLS; оператор строго >. В исходном snapshot для пары совпадают месяц, secondary, close/expected-expiration, различается порог. Значение публикуется за октябрь, хотя scheduled release в API относится к ноябрю; эти даты нельзя смешивать.

**Статус: `asserted_in_shared_value_binary_scope`.** При общем Expiration Value x из x>0.9 следует x>0.8. Свидетель строгого включения: x=0.9 даёт (0,1); x=0.8 даёт (0,0), x=1.0 — (1,1). Это условные числовые сценарии, совместимые с десятичной точностью.

У обоих контрактов также общий шаблон fallback, поэтому сама замена значения на один и тот же резервный x сохраняет порядок порогов. Но общий fallback должен применяться согласованно: его идентичный текст ещё не доказывает одинаковое решение при разных фактических процедурах. Вне указанной бинарной модели глобальные дискреционные исключения не проаудированы до гарантии.

Обнаружено расхождение: S3 с.2 устанавливает last trading 8:29 ET, а API secondary пары — 8:25 ET. Это не меняет арифметическое доказательство при одном x, но показывает, почему документы нельзя считать одним непротиворечивым текстом без версии/приоритета. API expected expiration — плановый метаданный срок, не тождество с юридическим Expiration time.

### Годовые пороги: ≥7% ⇒ ≥6.5%

A = `KXLCPIMAXYOY-27-P7.0`; B = `KXLCPIMAXYOY-27-P6.5`.

Один event, период и серия; в API отличаются только числовые пороги relevant primary. При общем ряде принимаемых месячных значений и согласованной стандартной процедуре достижение высокого порога влечёт достижение низкого. Статус — `asserted_in_shared_series_binary_scope`; реальные выплаты без условий не сертифицируются.

Свидетель строгого включения в модели: максимум ряда 6.7%. Выбранная пара сохраняет направление и при строгом, и при нестрогом прочтении каждого порога: 7.0 выше 6.5. Но выявленная граница `above`/`at least` остаётся unresolved для индивидуальных payoff-функций. Разные пороги способны завершаться в разные моменты; извлекать обе Expiration как единую фиксированную дату нельзя.

Не выбирать удобную ветвь автоматически. Здесь эта деталь не создаёт связи между металлами, но полезна как пример нужного error taxonomy.

## 5. Общие исключения: что меняется в постановке исследования

S7 §6.3(c), с.62, предусматривает определение выплат, когда значение или применимость критерия нельзя установить: среди методов названы последняя торговая цена и решение комитета. Следовательно, даже обозначение Binary Contract не исключает из полного договора все небинарные ветви. S7 §§7.1–7.2, с.64, регулирует review и изменение источника, Underlying, спецификации и срока. Эти полномочия надо хранить как scope/exception, а не пытаться предсказывать их использование.

Некоторые старые product templates ссылаются на 6.3(b)/(d) с формулировками, не совпадающими с нумерацией актуальной v1.29. Нельзя механически читать новую статью по старому номеру как тот же пункт. Точное применимое правило и опубликованные поправки требуют восстановления истории. Мы не делаем вывода о юридическом приоритете API против PDF.

Для CPI также нельзя автоматически переносить обычные сезонные пересмотры на unadjusted YoY. BLS описывает отсутствие рутинных revisions CPI-U/CPI-W из-за запоздалых данных, но допускает исправление обнаруженных ошибок; сезонно скорректированные ряды имеют собственный режим пересмотра. Поэтому «revision risk» здесь конкретное проверяемое поле, а не утверждение, будто все CPI обычно массово переписывают. [BLS, Correction and revision policies](https://www.bls.gov/opub/hom/cpi/presentation.htm), [seasonal adjustment](https://www.bls.gov/cpi/seasonal-adjustment/using-seasonally-adjusted-data.htm).

## 6. Исследовательский вывод

Проверка шести специально выбранных пар показывает, что числовое включение и отношение полных выплат требуют разных оснований. При одном общем значении резолюции порядок нижних порогов доказывается алгеброй. Для межсерийной пары одинаковых названий показателя недостаточно: резервные процедуры, сроки и версия источника должны быть согласованы отдельно. Обнаруженные различия обосновывают условный вывод или отказ от безусловного утверждения, но сами по себе не доказывают реализуемый контрпример к выплатам.

Этот аудит не измеряет precision/recall, частоту расхождений на площадке или качество модели и не заменяет независимую разметку. Его воспроизводимый результат — конкретные поля, выдержки источников и открытые предпосылки, которые можно проверять на новых парах.

Следующий технический шаг: добавить `binding_status`, `document_version`, `statistical_period`, `publication_time`, `expiry_cutoff`, `revision_policy`, `fallback`, `operator_conflict` и `standard_binary_scope` в evidence schema. Для обучения и оценки различать `asserted_in_declared_scope`, `conditional` и `unsupported`, не подменяя ими истинность самого договорного отношения.
