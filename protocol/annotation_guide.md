# Протокол разметки v0.1

Это предложение для будущего исследования. Здесь нет готовой человеческой gold-разметки.

## Единица и границы

Пара версий бинарных контрактов A/B на момент snapshot. Цель: ограничения на выплаты по правилам, а не предположение о совместном движении цен. Фиксировать площадку, ID, event ID, полный текст, время получения, source URL, SHA256. Для каждой площадки проверить источники уточнений и документов серии. Неполный API-текст не считать полным договором.

Нормировать выплаты к единице; сначала binary eligibility: yes/no без неоднозначного refund/void/50-50. Если исключения допускают небинарный исход, либо явно условная постановка «при стандартном бинарном резолве», либо `out_of_scope`. Нельзя молча превращать отмену в No.

## Сначала восстановить каждый контракт

1. Кто/что является объектом события, какой точный предикат.
2. Метрика, единицы, порог, строгая/нестрогая граница, округление.
3. Начало/конец окна, timezone, «к моменту», «в момент» или «хотя бы раз за окно».
4. Источник результата, место измерения, предварительная/окончательная публикация, revision policy.
5. Перенос, отмена, замена участника, fallback, уточнения, правила серии.
6. Для каждого заполненного поля указать дословный фрагмент и его поле/позицию. Отсутствующие данные обозначить null.

## Четыре состояния вместо одного знака

Для `(A,B) = 00,01,10,11` независимо разметить:

- `forbidden`: при принятых и записанных предпосылках состояние противоречит правилам; указать доказательство и цитаты.
- `possible_witness`: есть конкретный сценарий, согласующийся с обоими правилами; указать сценарий.
- `unknown`: данных недостаточно или неоднозначность не разрешена.

Ненайденное доказательство запрета не означает доказанную возможность. Ненайденный контрпример не означает доказанный запрет. LLM explanation не является формальным доказательством: отдельно проверяются извлечение и применимость шаблона.

| Вывод | Требуемые запреты |
|---|---|
| A implies B | 10 |
| B implies A | 01 |
| equivalent | 01 и 10 |
| mutually_exclusive | 11 |
| collectively_exhaustive | 00 |
| complements | 00 и 11 |

Метки могут пересекаться. `A implies B` означает нестрогое включение. Для strict subset дополнительно требуется возможный свидетель 01. `no_hard_relation` ставить лишь при свидетельствах всех четырёх состояний; это НЕ статистическая независимость. Если ни один тип не установлен и не все состояния имеют свидетельства, ставить `undetermined`. Уже обоснованные метки сохранять, даже когда другие состояния остаются unknown. Все четыре оценки должны использовать один согласованный набор предпосылок. Если все состояния запрещены, отклонить вывод и проверить несовместимость предпосылок или ошибку разметки.

`proof_status=unsupported` нельзя превращать в подтверждённую связь. `human_review_needed` означает предварительный кандидат. `formal_template` становится проверенным только после внешней проверки template ID, параметров и корректности их извлечения; самоназвание от LLM ничего не доказывает.

Граф из одних импликаций, эквивалентностей и исключений всегда допускает all-No. Поэтому SAT сам по себе может ничего не проверять. Добавлять только обоснованные правилами constraints существования/исчерпываемости; проверять, продолжаются ли локальные свидетельства возможности до глобального решения, и изучать минимальные конфликтующие подмножества. Совместимость формул необходима, но недостаточна для истинности их перевода из текста. Условно бинарная постановка не даёт безусловной гарантии выплаты при возможном void/refund.

## Трудные отрицательные пары

Одинаковая тема/заголовок, но разные дата, станция, источник, метрика, оператор порога, timezone или fallback. Также «выиграет выборы» против «вступит в должность», «пересечёт порог до даты» против «будет выше в момент даты». Для каждой такой пары не только отметить различие, но и проверить, действительно ли оно разрушает конкретное заявленное отношение.

## Как получить надёжную разметку

Сначала 30–50 пар, двое независимо, затем обсуждение расхождений и новая версия инструкции. Скрыть цену, результат, ответы моделей, названия сравниваемых систем. Сохранить исходные ответы обоих, adjudicated label, причину расхождения; не стирать disagreement. Для основных меток — agreement и Cohen κ с per-class counts; для multi-label — согласие по каждому запрету, отдельно доля unknown. Одна разметка ассистентом не заменяет двух экспертов.

Челлендж-набор намеренно обогащается трудными примерами и НЕ оценивает распространённость связей на площадке. Отдельный вероятностный audit sample из зафиксированной совокупности нужен для precision/coverage в эксплуатации; сохранять вероятности включения и веса, если выборка стратифицирована.

## Split и метрики

Разделять семьи событий/шаблонов до генерации пар: все пороги одного выпуска, перефразировки и синтетические мутации остаются в одном split. По возможности компоненты рынка целиком в одном split; не делить случайные пары с общими вершинами. Дополнительные тесты: held-out venue, будущие snapshots, unseen domain. Это труднее, чем простой random split.

Retrieval Recall@20/50/100 измерять на небольших полностью размеченных блоках, включая невыданные пары; оценка лишь по top-k выдаче не измеряет recall. Classification сравнивать на одинаковых кандидатах и одинаковых полных входах. End-to-end считать с потерями retrieval. Для selective classifier: precision при заданной coverage и coverage при целевой precision с доверительными интервалами. Отчёт по каждому отношению, macro-F1 на решённых gold случаях, доля abstain и отдельное качество на ambiguous случаях.

Порог abstention выбрать на dev; test не трогать. В сравнении цепочек агентов учитывать суммарные токены, стоимость, latency, число вызовов и одинаковый доступ к исходным документам. Bootstrap по семействам событий; доверительные интервалы на десятках зависимых пар не выдавать за надёжную оценку.

Resolution audit — вспомогательный тест опровержения: для A implies B запрещено только 10, для exclusion только 11, для equivalence 01/10. Один непротиворечащий итог не доказывает правило. Unknown/void сохраняются отдельно.
